# Community Partner Programs

Community Exchange is event-scoped by design. That protects participant consent, but it creates a separate operator problem: if two communities repeatedly create value together, they should not have to rediscover the same collaboration pattern from scratch every time.

Partner Programs solve that setup problem without weakening the event boundary.

## What a program remembers

A program stores only durable operator configuration:

- community A;
- community B;
- a human-readable program name;
- one to six reviewed Beacon domains;
- approval from both community owners;
- whether the reusable program is active, paused, or retired.

Example:

**Founder Operators Exchange**

Community A: founder network
Community B: experienced operator network
Domains: hiring, product, operations, mentorship

Or:

**Research ↔ Industry Bridge**

Community A: university research network
Community B: industry partner community
Domains: research, technical, partnerships, hiring

The program does not store participant identities, member rosters, historical target lists, or a reusable person-level recommendation graph.

## What a program never remembers as authority

A reusable program does not preserve:

- a participant's affiliation from an old event;
- badge visibility;
- exchange opt-in;
- a peer's declared intent;
- a historical live-field relationship;
- a past warm-introduction route;
- prior event exchange approval as current-event approval.

This is the core rule:

> **Configuration can compound. Consent cannot be inherited.**

## Activation flow

1. One community owner proposes a program.
2. The other community owner explicitly approves it.
3. The program becomes reusable.
4. At a future event, the host can see the program only if both communities are active partners of that event.
5. The host chooses **Use**.
6. Beacon creates a new event-specific exchange in `proposed` state.
7. Both community owners must approve the new event exchange again.
8. Individual participants must still verify affiliation and opt into exchange for that event.
9. A live peer bridge still requires a real declared-fit intersection.

A reusable program therefore reduces repeated configuration cost while keeping every privacy and consent boundary intact.

## Why this compounds

Without programs, every community collaboration is an isolated event configuration.

With programs, Beacon can support a durable network of community-to-community operating relationships:

**community pair discovers useful structure**
→ **owners preserve the structure as a program**
→ **future event host can reuse the structure quickly**
→ **event-specific consent resets**
→ **new cohort produces new evidence**
→ **community portfolio becomes more informative**

The compounding asset is the operating relationship, not a harvested member graph.

## Growth pathway

This creates a credible community-led distribution motion for Beacon:

- one accelerator can maintain a program with an investor network;
- one university alumni group can maintain a program with an employer community;
- one technical community can maintain a program with a founder community;
- one creator community can maintain a program with a brand/operator community;
- one professional association can maintain programs with adjacent chapters or disciplines.

A new community does not merely add users. It can add reusable bilateral programs with existing communities. Each accepted partner program creates another reason for both communities to bring Beacon into future events.

That is a network effect at the operator layer rather than a public follower graph.

## Kill switches

Either community owner can pause future reuse.

Paused means the program is retained as configuration but cannot be offered to new events.

A paused program can be reactivated only because both owners already approved the underlying program. It still does not bypass event-specific exchange approval.

A retired program is treated as intentionally closed for future reuse.

## Evidence interpretation

Program reuse should eventually be evaluated using the existing community exchange portfolio, not a public program score.

Beacon may show an owner private evidence such as:

- number of supported event exchanges using the same pair;
- cross-community mutual outcomes;
- declared-fit composition;
- repeat event coverage.

Beacon should not expose:

- a public ranking of partner programs;
- a "best community" leaderboard;
- individual member conversion rates;
- hidden estimates of community quality;
- automatic program activation based on historical performance.

Historical evidence can help operators decide whether to reuse a program. It cannot activate one.
